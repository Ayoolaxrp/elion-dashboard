# Client Measurement Framework — Before → ELION → After

Purpose: capture the same operational metrics BEFORE implementation and AFTER
launch so the first engagement produces honest, real proof (and identifies
where the system is or isn't working). The goal is a documented
**Before → ELION → After** story — not fabricated numbers.

Fill this in during the discovery call (Before), and again 30 days after launch (After).

## 4. During implementation (recorded, not guessed)

- [ ] Baseline metrics captured (section 2) and agreed with the owner
- [ ] Screenshots/sample of the current enquiry experience captured
- [ ] Systems deployed: Lead Response / Follow-Up / Booking / Other
- [ ] Go-live date
- [ ] Configuration documented (channels, hours, messages, pricing info)
- [ ] Owner trained + credentials handed over
- [ ] Known limitations at launch (e.g., calendar not connected yet) recorded

## 5. After-launch measurement (30 days)

- [ ] Re-measure every metric in section 2
- [ ] Capture the automated first-response time (from system logs)
- [ ] Count follow-ups sent automatically
- [ ] Count bookings created automatically
- [ ] Count escalations / human handoffs (things the AI couldn't handle)
- [ ] List any failures or gaps (integration down, missed leads) — include honestly
- [ ] Owner interview: what changed, what's still painful, what they'd add

## 6. The proof write-up (only from real measurements)

> Before: [business] received ~[X] enquiries/week, replied to [Y], average
> response [Z]. [N]% converted to bookings.
>
> ELION deployed: [systems].
>
> After: [X2] enquiries/week, first response in [seconds], [Y2] follow-ups,
> [Z2] bookings/week, [N2]% conversion.
>
> The measurable change: [delta]. Remaining gaps: [honest list].

Rule: every number above must trace to a measurement taken in sections 2–5.
If a number wasn't measured, write **not measured** — never estimate in public proof.
